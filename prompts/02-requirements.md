# 02. 요구사항 구조화 + 질의 도출 (STEP 1)

- 입력: 기획서 원문 (선택: 피그마 텍스트 레이어·프레임 목록, 이전 질의에 대한 답변)
- 출력: 요구사항 JSON (`schemas/requirement.schema.json`) + 질의 목록
- 사람이 할 일: 질의에 답한다. 답변이 모이면 `<answers>`에 넣고 다시 실행해 요구사항을 갱신한다

---

## 프롬프트

당신은 기획서를 테스트 관점에서 분석하는 QA 분석가입니다. 요약하지 말고, 아래 추출 스키마의 항목을 기획서에서 찾아 **구조화된 데이터**로 옮기세요.
이 결과는 다음 단계에서 테스트 조건을 기계적으로 조합하는 데 쓰입니다. 기획서에 없는 내용을 채워 넣으면 이후 모든 TC가 틀어지므로, 적혀 있지 않은 값은 비워 두고 질의로 돌리세요.

프로젝트 지식의 공통 규칙집(rulebook)은 기획서에 없는 값을 채울 때만 참조하고, 그렇게 채운 값에는 규칙 코드를 출처로 붙이세요.

<spec>
{기획서 원문 — 페이지 번호가 있으면 유지}
</spec>

<figma>
{선택: 피그마 프레임명과 텍스트 레이어 원문, 배리언트 목록. 없으면 "없음"}
</figma>

<answers>
{선택: 이전 질의 답변 "Q-01: 답변" 형식. 없으면 "없음"}
</answers>

### 추출 스키마
| 분류 | 추출 항목 |
|---|---|
| 기본 | 문서 버전, 작성일, 변경 이력 |
| 범위 | 대상 플랫폼(AOS/iOS/웹), 지원 OS·브라우저 최소 버전, **비대상(이번 범위 제외)** |
| 화면 | 화면 목록, 진입 경로, 화면 간 이동 관계 |
| 요소 | 버튼, 입력창, 목록, 노출 문구 (라벨 원문 그대로) |
| 동작 | 각 요소 선택 시 결과, 이동 화면 |
| 조건 | 노출 조건, 활성 조건, 권한, 회원 등급 — 조건별 가능한 값 전부 |
| 입력 규칙 | 최소·최대 길이, 허용 문자, 형식, 필수 여부 |
| 상태 | 로딩, 빈 목록, 에러, 성공, 타임아웃 |
| 문구 | 에러 메시지, 토스트, 팝업 문구 **원문** |
| 데이터 | 저장 대상, 갱신 시점, 유지 기간 |
| 연동 | API, 외부 서비스, 푸시, 딥링크 |
| 타이머 | 자동 전환·만료 등 시간 기반 동작과 초 단위 값 |

### 모호성 탐지 → 질의
다음 패턴을 찾으면 해당 값을 추측하지 말고 질의(`questions`)를 만드세요. 질의는 개발자·기획자가 한 줄로 답할 수 있게 구체적으로 쓰고, 가능하면 선택지를 제시하세요.

| 패턴 | 예시 | 질의 방향 |
|---|---|---|
| AMB 판정 불가 표현 | "정상 노출", "적절히 처리" | 어떤 화면·문구가 노출되는가 |
| NUM 수치 미기재 | "잠시 후 이동" | 정확히 몇 초인가 |
| TXT 문구 미정의 | "에러 메시지 노출" | 문구 원문은 무엇인가 |
| CND 조건 미완결 | "A일 때 B" (A가 아닐 때 없음) | A가 아닌 경우의 동작은 |
| REF 기존 정책 참조 | "기존과 동일" | 참조할 정책 문서·화면은 무엇인가 |
| CON 상충 | 같은 항목이 페이지마다 다름 | 어느 쪽이 최신인가 |
| EXC 예외 미기재 | 실패·타임아웃 언급 없음 | 실패·타임아웃 시 동작은 |
| FIG 기획서-피그마 불일치 | 문구·화면·배리언트·이동 경로 차이 | 어느 쪽이 최종인가 |

피그마가 주어졌다면 다음도 대조하세요.
- 기획서 문구 vs 피그마 텍스트 → 불일치 시 FIG 질의
- 기획서 화면 목록 vs 피그마 프레임 → 한쪽에만 있는 화면 표시
- 기획서 조건 vs 피그마 배리언트(Disabled/Error/Empty) → 배리언트는 있는데 기획서에 조건이 없으면 CND 질의
- 텍스트 말줄임·줄 수 제한 → 긴 문자열 처리 조건으로 기록

`<answers>`가 있으면 답변을 반영해 해당 필드를 채우고, 답변된 질의의 `status`를 `answered`로 바꾸세요. 답변을 근거로 채운 값의 출처는 `질의 Q-xx 답변`으로 적으세요.

### 출력 형식
아래 두 블록만 출력하세요.

```json

  "scope": { "platforms": [], "minVersions": {}, "outOfScope": [] },
  "screens": [

      "screen": "화면명",
      "entryPaths": [],
      "elements": [ { "id": "E-01", "type": "button|input|text|list|image|toggle|popup|toast", "label": "원문", "action": "", "enabledWhen": "", "source": "p.x" } ],

      "states": [ { "name": "loading|empty|error|success|timeout", "behavior": "", "message": "", "source": "" } ],
```

### 분석 메모
- 기획서 원문에서 인용했으나 스키마에 넣지 못한 내용 (있으면)
- `blocking: true` 질의 수와, 그 질의 때문에 TC 생성을 보류해야 하는 화면

규칙:
- `label`, `message` 등 문구 필드는 기획서 원문을 한 글자도 바꾸지 말고 옮기세요.
- 모든 항목에 `source`(페이지 또는 섹션)를 붙이세요. 규칙집으로 채운 값은 `규칙집: 코드`.
- `blocking`은 답이 없으면 기대결과를 쓸 수 없는 질의에 true, 답이 없어도 다른 TC는 쓸 수 있는 부가 질의에 false.
